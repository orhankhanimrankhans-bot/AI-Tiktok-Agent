# Jarvis Windows Deployment Guide

## Deployment architecture

Jarvis code and user state are intentionally separated:

```text
%LOCALAPPDATA%\Programs\Jarvis\        installed application files
%LOCALAPPDATA%\Jarvis\
├── .env                               user configuration and API keys
├── data\jarvis_memory.db              conversation and pending-task memory
├── logs\                              structured logs and crash reports
├── prompts\                           user system prompts
├── backups\                           automatic and manual backup archives
└── updates\                           verified packages and rollback files
```

Source development retains the existing project-local paths. Frozen builds automatically select `%LOCALAPPDATA%\Jarvis`, or `JARVIS_USER_DATA_DIR` when explicitly configured.

Installers and update packages never contain or overwrite `.env`, `data`, `logs`, `prompts`, `backups`, or `updates`.

## Reproducible build process

Requirements:

- Windows 10/11 x64;
- Python 3.12 x64;
- PowerShell;
- dependencies pinned in `requirements-windows.lock`;
- optional Inno Setup 6 for a setup executable.

Run:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build_windows.ps1
```

The script:

1. creates isolated `.build-windows` virtual environment;
2. installs exact pinned dependencies;
3. runs the complete automated suite;
4. builds from `packaging/Jarvis.spec` with PyInstaller;
5. prints SHA-256 for `dist/Jarvis/Jarvis.exe`.

The spec excludes tests, user state, and unused training/scientific stacks. UPX is disabled to avoid machine-dependent compression output.

## Creating the Windows installer

After PyInstaller succeeds, compile:

```powershell
iscc packaging\Jarvis.iss
```

Expected output:

```text
dist\installer\Jarvis-2.0.0-rc1-Setup.exe
```

The installer uses per-user privileges and installs under `%LOCALAPPDATA%\Programs\Jarvis`. It may create Start Menu and optional desktop shortcuts. Uninstalling application binaries does not remove `%LOCALAPPDATA%\Jarvis` user data.

Update the version in both `jarvis/__init__.py` and `packaging/Jarvis.iss` before a release.

## Windows installation

1. Verify the published installer SHA-256:

   ```powershell
   Get-FileHash .\Jarvis-2.0.0-rc1-Setup.exe -Algorithm SHA256
   ```

2. Run the installer as the normal Windows user; administrator rights are not required.
3. Create `%LOCALAPPDATA%\Jarvis\.env` from `.env.example`.
4. Add required credentials such as `OPENAI_API_KEY`; never place real credentials in the installation directory.
5. Launch Jarvis from the Start Menu.
6. Open System Health and confirm configuration, database, plugins, microphone, and optional FFmpeg status.

## Update manager

`UpdateManager` supports:

- semantic version comparison;
- remote JSON manifest checks;
- background dashboard notification;
- streamed download to `.zip.part`;
- SHA-256 validation before atomic rename;
- zip-path traversal rejection;
- protected user-path filtering;
- staged installation journal;
- backup of replaced application files;
- automatic rollback if any copy fails.

Manifest format:

```json
{
  "version": "0.2.0",
  "url": "https://updates.example.com/jarvis-0.2.0.zip",
  "sha256": "64-lowercase-hex-characters"
}
```

Configure:

```dotenv
JARVIS_UPDATE_MANIFEST_URL=https://updates.example.com/manifest.json
```

The Dashboard Updates page checks in a background thread and displays notifications. Download/application requires explicit release workflow approval. On Windows, application-file replacement should run after Jarvis exits (for example through the installer or a small updater helper) because the running executable may be locked.

## Safe upgrade procedure

1. Create a backup from Dashboard → Backups.
2. Publish the new zip and its SHA-256 manifest over HTTPS.
3. Check the update in Dashboard.
4. Download and validate with `UpdateManager.download()`.
5. Close Jarvis before replacing application files.
6. Apply the staged package or run the newer Inno Setup installer.
7. Restart and inspect System Health, Logs, and conversation memory.
8. Keep rollback files until the release passes smoke validation.

User state is never part of the application-file replacement set.

## Backup strategy

`BackupManager` protects:

- `data/jarvis_memory.db` using SQLite's online backup API;
- `.env` configuration;
- all files below `prompts/`.

Backups are ZIP archives under `%LOCALAPPDATA%\Jarvis\backups`. Packaged builds default to one automatic backup per 24 hours. Source development defaults to opt-in:

```dotenv
JARVIS_AUTO_BACKUP=1
```

Dashboard supports Create backup and Restore latest. Restore requires explicit confirmation.

### Restore validation

Before replacement, restore:

- rejects absolute paths and `..` traversal;
- rejects unexpected archive members;
- runs SQLite `PRAGMA integrity_check`;
- closes every SQLite handle explicitly on Windows;
- atomically replaces validated state files.

After restoring, restart Jarvis so configuration and memory singletons reload cleanly.

## Rollback procedure

### Failed application update

`UpdateManager.apply()` records changed and newly created files. On failure it:

1. deletes files newly created by the failed version;
2. restores every replaced file from `updates/rollback-<old>-to-<new>`;
3. removes the incomplete journal;
4. reports a safe failure notification and structured rollback log.

If manual recovery is needed, close Jarvis and copy rollback directory contents back into `%LOCALAPPDATA%\Programs\Jarvis`, preserving relative paths.

### Failed user-state restore

Do not delete the backup archive. Close Jarvis, select the last known-good archive, and restore again. If necessary, extract only the validated database/configuration artifact into `%LOCALAPPDATA%\Jarvis` while Jarvis is stopped.

## Crash reports and startup diagnostics

Unhandled process exceptions create redacted JSON reports under:

```text
%LOCALAPPDATA%\Jarvis\logs\crashes\
```

Reports include timestamp, Python/platform, exception type, sanitized message, and sanitized traceback. Lines containing API-key, token, secret, password, or authorization markers are redacted.

Startup diagnostics report:

- packaged/source mode;
- user-data path writability;
- SQLite integrity/missing/error state;
- configuration validity and issue count;
- FFmpeg availability.

Diagnostics never expose API-key values.

## Dashboard deployment pages

- **Updates:** installed version, manifest status, notifications, background update check.
- **Backups:** archive list, background backup creation, confirmed restore-latest action.
- **System Health:** startup, configuration, database, API, plugin, and resource diagnostics.

Maintenance actions run on `DashboardActionThread`; the Qt event loop remains responsive, and late results are suppressed after shutdown.

## Current limitations

- Code signing certificate integration is not included; production installers and update zips should be Authenticode-signed.
- The dashboard checks and notifies; silent unattended installation is intentionally not enabled.
- Replacing a running Windows executable requires shutdown/installer-helper coordination.
- Backup archives contain sensitive `.env` data and should be protected with Windows filesystem permissions or external encryption at rest.
- Hardware-specific voice, WhatsApp UI Automation, FFmpeg, and live TikTok/OpenAI smoke tests still require the target machine.
